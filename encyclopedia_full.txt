## 0. Honest framing (read first)

- "Zero errors" cannot be *proven* by testing. What you can do is make bugs **measurable and hard to hide**: (a) a written invariant for every money/state rule, (b) the invariants checked **after every action** in a long randomized session, (c) every failure reproducible from a seed, (d) a coverage table showing which case IDs were actually exercised. Release when: all P0/P1 case IDs are covered, the overnight session finds no invariant violation across several different seeds, and every mutation check is caught.
- Items marked **[RULE?]** depend on a business/legal rule the code or the owner must confirm. The agent must not guess these; it lists them as owner questions and tests them *parametrically* (the test reads the configured rule).
- Items marked **[UNVERIFIED-LAW]** are legal/regulatory points I could not verify for Algeria. They are written as *design patterns seen in other jurisdictions*; the owner/accountant decides if they apply.

## 0.1 Research findings that shape the tests (with sources)

**Sync (libSQL / Turso) â€” the mode matters, find out which one the app uses (Phase 0):**
- *libSQL Embedded Replicas*: reads are local and keep working offline, but **writes go to the cloud primary** and are reflected back; writes cannot work offline. Turso's own docs say embedded replicas only work where there is a file system, and for offline writes/bidirectional sync they recommend the newer `turso.sync` (local writes + explicit `push()`/`pull()`). â†’ https://docs.turso.tech/sdk/python/reference , https://turso.tech/blog/turso-offline-sync-public-beta
- *Offline Sync (beta announcement)*: local writes sync later; at that announcement **conflict detection existed but resolution was "not yet implemented"** and it was "beta quality, not recommended for production". The newer Turso docs list a "Conflict Resolution" page. â†’ same blog, https://docs.turso.tech/ (Sync / Conflict Resolution)
- Earlier Turso blog describes strategies: silently discard local changes on conflict, or **manual/custom conflict resolution**. â†’ https://turso.tech/blog/introducing-offline-writes-for-turso
- With `readYourWrites` enabled on embedded replicas every write forces a network round trip; with it disabled you get local-write feel but replicas can lag. â†’ https://turso.tech/blog/sync-benchmark
- Practical advice from a third-party guide: if you need strong guarantees, serialize writes through one app instance or detect conflicts in your own code. â†’ https://botmonster.com/web-dev/turso-libsql-sqlite-edge-embedded-replicas/
- â‡’ **Consequence:** a POS must never rely on "last write wins" for money tables (sales, payments, stock, loyalty, cash drawer). Money data should be **append-only ledger rows with globally unique IDs** (per-device ID prefix/ULID/UUID) and balances derived from them. The tests below attack exactly this.

**Refunds & rounding**
- Partial refunds must be computed from the **amounts stored at sale time**, and rounding differences must be absorbed so the **sum of all refunds equals the original** (final refund gets the remainder). â†’ https://docs.litium.com/platform/areas/sales/order-fulfillment/rounding-off
- Discounts must be **allocated across lines**; refunding one line must refund its *share* of the discount, otherwise you over-refund. â†’ https://apps.shopify.com/refundmath
- A flat goodwill refund not tied to an item needs an explicit allocation rule across lines. â†’ https://paytia.com/glossary/partial-refund ; refunds are logged as returns/allowances tied to the original sale. â†’ https://stripe.com/resources/more/partial-refunds

**Loyalty**
- Refunding a sale removes earned points; if points were already spent the **balance can go negative**; already-converted rewards are not clawed back (policy choice). â†’ https://help.materialretail.com/loyalty/4aFUu3ni3pQBcUn1qsPaJW/why-a-loyalty-balance-could-be-negative/4aFUu3ni3rMv33ERjMhmuL , https://support.yotpo.com/docs/point-balance-for-refunded-orders
- Refunds under a **multiplier/bonus campaign** must reverse base *and* bonus points; partial refunds of multi-quantity items reverse proportionally. â†’ https://docs.gameball.co/tutorials/experiences/refund-handling
- Points used to pay for part of an order, then partial refund: only a proportional share of redeemed points is returned. â†’ Yotpo link above.

**Receipt printing (Arabic)**
- Thermal printers don't use PC fonts; unsupported characters become `?`/boxes. Arabic via code pages (e.g. Windows-1256 / ISO-8859-6) often prints **letters disconnected and in left-to-right order**; the dependable fix is **printing the receipt as an image (raster)**, at the cost of speed. One code page rarely covers two scripts, so mixed Arabic+French receipts need raster. â†’ https://docs.wcpos.com/hardware/printers/non-latin-receipts.md , https://www.b4x.com/android/forum/threads/126549 , https://www.b4x.com/android/forum/posts/914696/

**Phone trade-in / second-hand dealing [UNVERIFIED-LAW for Algeria]**
- Other jurisdictions require dealers to record make/model, **IMEI/serial**, seller name/address and a **copy of ID**, keep it â‰¥5 years (South Africa), forbid buying from **minors** and allow police **sell-hold notices** (Missouri bill), and pay by traceable means (Illinois bill). â†’ https://www.acts.co.za/second-hand-goods-act-2009/26_communication_equipment_records , https://documents.house.mo.gov/billtracking/bills131/sumpdf/HB1004I.pdf , https://ilga.gov/legislation/99/SB/09900SB0066.htm
- GSMA Device Check lets second-hand buyers check whether an IMEI is on a blacklist (stolen/lost) before buying. â†’ https://www.gsma.com/services/wp-content/uploads/2019/08/imei_panacea_07_08_19.pdf

**Repair shop**
- Typical ticket fields: device/IMEI/condition/accessories, problem, estimate, approved work, parts used, labor, **deposit collected, balance due, pickup status**; parts usage ties to stock; deposits protect against abandoned special-order parts. â†’ https://phppointofsale.com/repair-ticket-management.php , https://repairdesk.co/feature/repair-ticket-management
- Warranty claim eligibility pattern: ticket had warranty, invoice paid, claim inside period, status completed; **warranty period starts when status becomes Repaired/Completed**. â†’ https://help.repairdesk.co/knowledgebase/articles/1968825
- Inconsistent handling of deposits/split payments between staff is the classic source of ticket drift. â†’ https://blog.repairdesk.co/2026/04/13/how-repair-shops-speed-up-checkout-without-ticket-errors/

**v4 research â€” SQLite behaviours behind the new cases (re-check on the exact SQLite/libSQL build bundled in each app, desktop and mobile):**
- *WAL and `ATTACH`:* a transaction that changes several attached databases is atomic **per file but not as a set**; WAL needs all processes on the same host (no network share) and is not suited to transactions in the gigabyte range. â‡’ audit/outbox/archive in a second file breaks "sale + audit together" (DAT-71, SCL-84). â†’ https://www.sqlite.org/wal.html
- *Online backup API:* if another connection or process modifies the source while the backup runs, the backup is **restarted** at the next step, so on a busy DB it may never finish; other consistent-copy techniques exist (e.g. `VACUUM INTO`, which holds one long read snapshot). â‡’ measure backup *completion* under load (DAT-69). â†’ https://www.sqlite.org/c3ref/backup_finish.html
- *Deferred transactions in WAL:* a transaction that reads and then writes fails with `SQLITE_BUSY_SNAPSHOT` when another connection committed in between; the busy timeout does not fix it; known writers should start with `BEGIN IMMEDIATE`. â‡’ refund guard design (REF-88, DAT-60). â†’ https://www.sqlite.org/isolation.html
- *`VACUUM` and rowids:* the documentation says `VACUUM` may change the rowids of tables without an explicit `INTEGER PRIMARY KEY` (SQLite's own test notes say newer versions preserve them â€” do not rely on either); in WAL mode `VACUUM` cannot change `page_size`. â‡’ never store bare rowids as references (SCL-77, SCL-80). â†’ https://www.sqlite.org/lang_vacuum.html
- *FTS5:* the `trigram` tokenizer exists since 3.34; in `MATCH` text a hyphen, plus sign, colon or quote is query syntax, so raw user input such as `Ben-Ali`, `C++` or `a:b` raises an error unless quoted. â‡’ SCL-62. â†’ https://www.sqlite.org/fts5.html
- *From SQLite's documentation but **not re-checked** in this revision:* column types are advisory unless the table is `STRICT` (â‰¥ 3.37); `LIKE`, `lower()` and `upper()` fold only ASCII by default; `AVG()` and `total()` return floating point. â‡’ SCL-61, SCL-78. â†’ https://www.sqlite.org/datatype3.html , https://www.sqlite.org/lang_expr.html
- *Not verified:* Turso/libSQL plan quotas, inactivity/archival rules and per-database limits at the owner's plan (SCL-87, DAT-76) â€” read the provider's current pricing and limits pages.

### Engineering facts that drive the new cases (verify against the SQLite/libSQL version actually bundled â€” Phase 0)
- libSQL embedded replicas pull from the primary on an interval or an explicit `sync()`; there is no built-in "push this change to the other device now". So **"the drawer opens instantly on the mobile app" needs a push channel (WebSocket/SSE/push notification) that triggers a pull, or direct remote reads**; with plain polling the latency equals the poll interval. The tests therefore assert a **configured latency SLA**, not "instant" (DRW-01, SYN-21). **[RULE?]** choose the SLA with the owner (suggested starting point: p95 â‰¤ 3 s while online).
- An embedded replica is a **full copy** of the database. A phone that only needs warranty lookups still holds all customers, PIN hashes and sales unless the design limits what is replicated â†’ stolen-phone exposure (SYN-26, MOB-10).
- SQLite behaviours that bite at scale: `LIKE '%x%'` cannot use a normal index (full scan); `OFFSET n` pagination re-reads n rows; the bound-parameter limit is 32,766 in builds â‰¥ 3.32 (999 in older ones), so batched inserts and `IN (...)` lists must be chunked; `foreign_keys` and custom collations are **per connection**; a long-lived read transaction can block WAL checkpoints so the `-wal` file keeps growing; `VACUUM` needs free disk space about equal to the DB size.
- Blobs (ID scans, inspection photos) should not ride the row sync; they need their own upload path, so a row can arrive before its file (SYN-25, WAR-17).
- Android can kill a backgrounded app at any time, OEM battery managers delay background work, and Android Auto Backup can restore an **old** database file after reinstall â†’ a forked history (MOB-03, MOB-04, MOB-09).
- **Data-loss facts (v3):** in WAL mode with `synchronous=NORMAL` a power cut can drop the most recent committed transactions (the file stays consistent) â€” `FULL` gives durability at some speed cost (DAT-20, DAT-21). Deleting the `-wal` file or copying only the `.db` of a live database loses recent commits (DAT-24). `REPLACE INTO` deletes then inserts, which can cascade-delete child rows (DAT-40). Integer row ids without `AUTOINCREMENT` can be reused after deleting the highest id (DAT-41). Table-rebuild migrations drop indexes, triggers and foreign keys that are not recreated (DAT-51). A process kill does not prove power-loss safety because the OS cache survives it (4.11).
- **Refund facts (v3):** the refund basis is what the customer actually paid (net of every discount share), not the catalog price or the cash handed over; limits must be enforced where the data lives (database layer), because the UI, a second device or a forged call can all bypass a UI-only check (REF-30, REF-46).
- **Scale and loss facts (v4):** in WAL mode a transaction across `ATTACH`ed files is not atomic as a set (DAT-71, SCL-84); the backup API restarts when others write (DAT-69); a deferred readâ†’write transaction can fail with `SQLITE_BUSY_SNAPSHOT` (REF-88, DAT-60); `VACUUM` may renumber rowids of tables without an explicit `INTEGER PRIMARY KEY` (SCL-77); non-`STRICT` columns accept any type (SCL-78, G-33); `LIKE`/`lower()` fold only ASCII by default (SCL-61); `page_size` is fixed when the file is created (SCL-80); a FAT32 USB stick cannot hold a file of 4 GB or more (DAT-68); the sync backend is a replica, not a backup, and deleted-row markers can be purged before an offline device returns (DAT-77); an acknowledged cash refund is the hardest loss to see because the money has already left the drawer (REF-81).

## 4. LONG-SESSION TESTING (how to find bugs nobody thought of)

### 4.1 Why random + model + invariants
Hand-written tests only find bugs you imagined. A long session performs **thousands of random but valid business actions** against the real app while a **shadow model** (independent, BigInt-based, written in the test process) predicts the correct state. After every action (or every K actions) the runner compares model â†” app â†” DB â†” UI and checks Part 2 invariants G-01â€¦G-36. Any mismatch stops the session and saves a **replayable action log + seed**.

### 4.2 Architecture

### 4.3 Runner skeleton (adapt names; verify every command against Discovery)
```ts
import { mulberry32 } from '../lib/rng';
import { Model } from './model';
import { ACTIONS, FAULTS } from './actions';
import { checkAll } from './invariants';
import { Coverage } from './coverage';
import fs from 'node:fs';

describe('LONG SESSION', function () {
  this.timeout(Number(process.env.SESSION_MIN ?? 120) * 60_000 + 10 * 60_000);

  it('random business walk keeps every invariant', async () => {
    const seed = Number(process.env.SEED ?? (Date.now() % 1e9));
    const budgetMs = Number(process.env.SESSION_MIN ?? 120) * 60_000;
    const checkEvery = Number(process.env.CHECK_EVERY ?? 1);   // 1 = after every action
    const faultRate = Number(process.env.FAULT_RATE ?? 0.03);  // 3% of steps inject a fault
    const rnd = mulberry32(seed);
    const dir = `./long/logs/${seed}`; fs.mkdirSync(dir, { recursive: true });
    const log = fs.createWriteStream(`${dir}/actions.jsonl`);
    console.log('SEED=', seed);

    await invoke('e2e_reset_and_seed', { fixture: process.env.FIXTURE ?? 'long' });
    const model = await Model.fromApp();               // load seeded catalog/users/customers
    const cov = new Coverage();
    const t0 = Date.now();
    let step = 0;

    while (Date.now() - t0 < budgetMs) {
      const useFault = rnd() < faultRate;
      const pool = (useFault ? FAULTS : ACTIONS).filter(a => a.precondition(model));
      const action = pickWeighted(pool, rnd);
      const params = action.generate(model, rnd);       // all randomness from the seeded rnd

      log.write(JSON.stringify({ step, t: Date.now() - t0, action: action.name, params }) + '\n');
      try {
        await action.execute(params, model);            // drives UI/IPC AND updates the shadow model
      } catch (e) {
        await saveFailure(dir, step, action, params, e); // screenshot + DB copy + logs
        throw new Error(`Action failed at step ${step}: ${action.name} ${JSON.stringify(params)} :: ${e}`);
      }
      cov.hit(action.name, action.caseIds);

      if (step % checkEvery === 0) {
        const violations = await checkAll(model);       // compares model vs snapshot vs sampled UI
        if (violations.length) {
          await saveFailure(dir, step, action, params, new Error(JSON.stringify(violations)));
          throw new Error(`INVARIANT VIOLATION after step ${step} (${action.name}): ${JSON.stringify(violations)}  SEED=${seed}`);
        }
      }
      step++;
    }
    cov.write(`${dir}/coverage.json`);
    console.log(`OK: ${step} actions, SEED=${seed}`);
  });
});
```
Rules for the runner:
- **All randomness from the seeded PRNG.** No `Math.random()`, no `Date.now()` inside actions' decisions. Same seed + same build + same fixture â‡’ same run.
- Actions must call the **same production commands/UI paths** a user uses. ~70% through the real UI (selectors), ~30% through IPC for speed, rotating, so both paths stay honest.
- The shadow model is updated **from the business rule (oracle)**, not from the app's response. After each action the model's prediction is compared with the app.
- Illegal/forbidden actions are part of the walk (e.g. cashier tries a manager action, refund > paid, IMEI duplicate) and the model predicts a **rejection**; success of a forbidden action is a P0 finding.
- Keep a per-action `caseIds` list so coverage shows which Part 3 IDs were exercised.

### 4.5 Fault-injection design (how to inject in a Tauri e2e build)
- **Kill/relaunch:** terminate the app process at a random point during an action (OS kill, or `e2e_crash_after(step)` hooks inside transactions), then start a new WDIO session on the same e2e data dir; assert G-10 and that pending gateway approvals reconcile (PAY-06).
- **Offline:** e2e-only switch in the sync layer (`e2e_set_network(mode)`), plus optionally OS-level network block on the test machine.
- **Printer:** mock printer service in e2e build with modes `ok | offline | paper_out | slow:<ms> | drop_after:<bytes> | garble_codepage`; also a **real-printer pass** (manual or hardware-in-loop) for RCP-01/LBL-03.
- **Gateway:** modes from `e2e_set_gateway_mode` incl. random mix with fixed seed.
- **Clock:** an e2e-only clock source (`e2e_set_clock(offsetMs)`) that the app's time provider honors; never change the real OS clock on a dev machine.
- **Second device:** WDIO multiremote (2â€“3 instances) sharing one sync backend; the second device performs conflicting operations at fault steps (SYN-05/06/19).
- **DB lock:** an e2e command that opens a long write transaction from another connection for N ms.

### 4.7 Minimizing failures (so bugs are fixable)
When a run fails, `replay.ts` must: (1) re-run the saved `actions.jsonl` from a clean fixture to confirm it's reproducible; (2) **delta-debug** (remove chunks of actions, keep removing while the same invariant still fails) to a minimal sequence (usually < 20 steps); (3) emit a Markdown bug report: minimal steps, expected (oracle + rule source) vs actual, invariant ID, case ID, seed, build hash, screenshots, DB snapshot path.

### 4.8 Silent-bug detectors to run continuously (things humans never notice)
- **Rounding drift:** after every 500 actions, recompute totals from raw rows with integer SQL and compare with app-reported totals.
- **Orphans:** `PRAGMA foreign_key_check`, rows without parent, payments without sale, stock moves without document, loyalty rows without sale.
- **Duplicates:** (device_id, idempotency_key) uniqueness; duplicate receipt numbers; duplicate IMEI "in stock".
- **Stale UI:** every N actions reload the same screen from DB and compare with what the UI showed (cache/replica-lag bugs).
- **Unbounded growth:** table sizes, log size, memory/handles, in-memory queue lengths, WebView DOM node count.
- **Slow degradation:** per-action latency percentiles in windows of 1,000 actions; alert when p95 doubles.
- **Console/backend errors:** any `error`/`panic`/unhandled rejection line in captured logs fails the session, even if the UI looked fine.
- **Time bombs:** run the session with the e2e clock set to 31 Dec 23:59, leap day, month end, and +1 year to flush date bugs.
- **Cross-device staleness (v2):** every N actions compare the drawer/ticket/claim status shown on each online device with the server row; record the age of any difference; fail when it exceeds the SLA.
- **Name drift (v2):** for every document, `printed/rendered cashier name == stored snapshot == session user at creation`; a renamed or disabled user must not change old documents.
- **Hot-row drift (v2):** recompute customer counters (`total_spent`, `points_balance`, `visits`) from the ledger and compare, especially for the walk-in customer.
- **Plan regression (v2):** after every migration and every bulk import, re-run `EXPLAIN QUERY PLAN` for the hot queries (G-22) and compare with the baseline.
- **WAL/outbox growth (v2):** size of `-wal`, age and count of outbox rows per device; alert when either grows monotonically.
- **Stale-cache actions (v2):** try an action that needs fresh state (open drawer, redeem points, claim a warranty) from a device whose last sync is older than the threshold; it must be refused or revalidated.
- **Refund conservation (v3):** recompute Î£ refunded per line and per tender from raw rows and compare with G-29; any line above sold qty or net paid is P0.
- **Row-count monotonicity (v3):** counts of customers, products, sales, lines, payments, IMEIs never drop between snapshots except through an audited operation; a silent drop raises an alert (G-30).
- **Backup freshness and restore check (v3):** newest backup age â‰¤ RPO, restored copy matches source totals, off-machine copy exists (G-28); canary ids present everywhere (DAT-66).
- **Acknowledged-write ledger (v3):** every id the app confirmed is present after every relaunch (G-27).
- **Pooled-connection state (v3):** after each action no connection holds an open transaction (DAT-59).
- **Type discipline (v4, G-33):** after every import, sync apply and migration run `SELECT typeof(col), count(*) â€¦ GROUP BY 1` for every money, quantity, id and IMEI column; a non-integer money value or a numeric IMEI is P0.
- **Derived-data equality (v4, G-34):** rebuild counters, stock balances, summaries, FTS and search columns into temp tables every N actions and after every bulk job; compare with the stored copies.
- **Statement-count budget (v4, SCL-85):** count SQL statements and IPC calls per UI action; alert on N+1 patterns and on any action above its budget.
- **Space growth (v4, SCL-81):** per-table/index size delta every 1,000 actions; unexplained jumps and indexes larger than their table are flagged.
- **Device identity (v4, G-36):** each `device_id` registered once, heartbeats unique, ID ranges disjoint; two live heartbeats with one id is P0.
- **Account balances (v4, G-32):** per-customer receivable/credit recomputed from rows; negative balances without a credit flag fail.
- **Sequence gaps and external witnesses (v4, DAT-80, DAT-89):** gaps in per-device committed-transaction sequences and document counters compared with printed slips and settlement files.
- **Destructive-change log (v4, G-35):** any `DELETE`/`UPDATE` above N rows or on a ledger table outside the allowed job fails the session.

### 4.9 Multi-device long session (desktop + mobile + second desktop) â€” v2
- `long/multi.e2e.ts` uses WDIO **multiremote** with named instances `desktopA`, `desktopB`, `mobile`. Desktop = the Tauri WebDriver session; mobile = Appium (UiAutomator2) against an emulator or a real phone. **Verify in Discovery that the two drivers can run in one multiremote session**; if not, run the phone through a **headless client that uses the same sync/API layer** for volume, plus a smaller real-UI mobile pass (MOB cases).
- The shadow model gets a **per-device view**: `model.devices[d] = { online, lastSyncedAt, knownDrawerVersion, outbox[], loggedInUser }` next to the authoritative `model.truth`. It predicts what each device **should** show at time t given its connectivity and the SLA.
- Added actions (weights in 4.4): PIN login/switch, drawer open/close/force-close/handover on any device, simultaneous conflicting actions on two devices (`Promise.allSettled`), warranty inspection on mobile finished on desktop, cart park/resume across devices, plus faults: mobile to background/killed, network drop, push dropped/duplicated, device revoked, stale replica restored.
- Checks after every action, and a **quiesce check** every K actions (stop new actions â†’ bring all devices online â†’ wait â‰¤ settle time â†’ compare):
  1. **Freshness:** for each online device, the shown drawer/ticket/claim status and version equal the server's within the SLA; the latency histogram is stored and p95 must stay â‰¤ SLA.
  2. **No stale actions:** an action needing fresh state on an offline/stale device is refused or queued per rule.
  3. **Single winner:** concurrent open/close/refund/claim â†’ exactly one success (G-17, REF-14).
  4. **Convergence:** G-12, G-17, G-24, G-26 identical on every device after quiesce.
  5. **Attribution:** every new document's stored user/device/drawer equals what the model says was logged in on that device at that moment, and the rendered receipt name equals the stored snapshot (G-19).

### 4.11 Data-loss drills â€” v3
- **Purpose:** prove G-27 (acknowledged = durable), G-28 (recoverability), G-30 (no destructive cascade). Run on the small fixture and on a production-size copy (`scale-1m`, `scale-3y`).
- **Acknowledged-write ledger:** the harness appends every id the app confirmed (sale, refund, payout, drawer event, trade-in, ticket) to a plain file **outside** the app's data dir, flushed to disk. After every fault and relaunch it asserts that each id exists with identical totals.
- **Fault set:** (a) `kill -9` at random moments, including e2e crash hooks between every statement of a sale/refund; (b) **hard power-off of a VM** (hypervisor power-off or snapshot revert) during sale, refund, checkpoint, `VACUUM`, backup, import, migration, sync apply â€” a process kill does not prove power-loss behaviour because the OS cache survives it; (c) disk full (small quota volume); (d) read-only volume; (e) removable drive pulled; (f) delete/rename the `-wal` file; (g) flip random bytes in a *copy* of the DB and of a backup; (h) restore an old backup; (i) wipe the local DB and rebuild from the sync backend; (j) wipe the backend and rebuild from a device; (k) clock jump before retention/rotation jobs.
- **Fault set, v4 additions:** (l) backup to a FAT32 stick or a small quota volume until it is full; (m) backup while 5 sales/min and a 1 M-row import run (does it ever finish?); (n) restore a backup from every older release into the newest build, and a newer backup into an older build; (o) clone the app-data folder/VM image to create a second device with the same `device_id`; (p) open the live DB in an external tool, hold a read transaction, then run a write and a `VACUUM`; (q) kill between the two commits of any multi-file operation (archive move, audit file); (r) keep a device offline longer than the tombstone/idempotency-key retention, then reconnect; (s) a bulk update that blanks a column on one device, then sync; (t) licence expiry and backend quota exhaustion during a shift; (u) delete the `-wal` of a copy and compare lost transactions with the durability policy (DAT-24).
- **Selective-restore and witness drills (v4):** recover a deleted slice of customers/products from a backup without a full restore (DAT-78); run the daily reconciliation against terminal/gateway settlement files and drawer counts (DAT-80); run the gap finder after every restore (DAT-89).
- **After each fault:** `PRAGMA integrity_check`, `foreign_key_check`, G-01â€¦G-13, G-27, then a **reconciliation report** (what is missing, extra or inconsistent, and why). Any acknowledged id missing outside the documented durability policy = P0.
- **Disaster-recovery rehearsal (quarterly script):** new PC â†’ restore the newest off-machine backup â†’ join sync â†’ sell one item â†’ run reconciliation. Record RPO (data window lost) and RTO (time until selling) against the owner's targets.
- **Destructive-operation drill:** try each destructive action (mass delete, bulk edit, import-replace, merge, purge, factory reset) as cashier, manager and owner; confirm guards, restore point, export, audit, and that undo works.
- **Continuous canaries:** a synthetic sale/product with a known id is written daily and must appear in each verified backup and on every device (DAT-66).

### 4.13 Reference oracles for refunds (put in `e2e/long/oracle/`, tested code) â€” v4
All values are integers: money in minor units, quantities in milli-units. Use BigInt in TypeScript and 128-bit integers in Rust â€” `discount Ã— line amount` overflows a 64-bit integer at the maximum values of MNY-06 (REF-87). The oracle works on non-negative magnitudes; handle signs outside it. If the owner's rounding rule is not half-up, swap only the rounding step; the telescoping structure is what keeps sums exact.
```ts
// oracle/money.ts
// 1) Largest-remainder allocation of an invoice discount D over line bases b[] (0 <= D <= sum(b), CRT-04).
//    Stored per line at sale time; a refund never recomputes it from current rules.   net_i = b[i] - share[i]
export function allocateDiscount(D: bigint, b: bigint[]): bigint[] {
  const B = b.reduce((x, y) => x + y, 0n);
  if (D === 0n || B === 0n) return b.map(() => 0n);
  const share = b.map(bi => (D * bi) / B);                       // floor
  const frac  = b.map(bi => (D * bi) % B);
  let r = D - share.reduce((x, y) => x + y, 0n);                  // 0 <= r < number of lines
  const order = b.map((_, i) => i).sort((i, j) => (frac[j] > frac[i] ? 1 : frac[j] < frac[i] ? -1 : i - j));
  for (let k = 0; r > 0n; k++, r--) share[order[k]] += 1n;       // ties go to the lower line index
  return share;
}
// 2) Partial refund by quantity. Line sold Q (milli-units), net paid N, already refunded R.
//    cum(0) = 0 and cum(Q) = N, so the last step takes the remainder automatically, in any order or chunking.
export const cum = (N: bigint, R: bigint, Q: bigint) => (2n * N * R + Q) / (2n * Q);   // round half up
export const refundStep = (N: bigint, Q: bigint, R: bigint, dq: bigint) => cum(N, R + dq, Q) - cum(N, R, Q);
// 3) Split a refund A across the original tenders in the configured order (e.g. card first, or reverse payment order);
//    each leg is capped by what is still refundable on that tender (paid minus already refunded; change is never refundable).
export function splitTenders(A: bigint, remaining: { tender: string; rem: bigint }[]) {
  const legs: { tender: string; amount: bigint }[] = []; let left = A;
  for (const t of remaining) { const x = left < t.rem ? left : t.rem; if (x > 0n) legs.push({ tender: t.tender, amount: x }); left -= x; }
  if (left !== 0n) throw new Error('REFUND_EXCEEDS_REFUNDABLE');
  return legs;
}
```
- **Restocking fee F â‰¤ A:** the customer receives A âˆ’ F; the fee is its own income line; allocate A across lines with (1)+(2) *before* subtracting the fee.
- **Receivable first (credit sales, REF-65):** outstanding O = invoice net âˆ’ paid so far; of a refund A, `min(A, O)` reduces the receivable by credit note and only `A âˆ’ min(A, O)` goes to tender legs via (3).
- **Property tests (fast-check / proptest):** (a) Î£ shares = D and share â‰¤ base; (b) Î£ steps = N for any chunking or order and every cumulative â‰¤ N (REF-86); (c) tender legs conserve A and respect caps; (d) replaying a request with the same key changes nothing (REF-47); (e) results at maximum amounts equal the BigInt oracle (REF-87). The snippet above passed 20,000 random cases of (a)â€“(c) plus a 64-bit-overflow case when it was written; re-run it in your own harness.
