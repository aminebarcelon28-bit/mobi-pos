## Root cause of the earlier worktree-only two-instance failure (not "disappeared")

The earlier harness started **two concurrent `wdio` processes**. Its failure modes,
both captured in the logs:

1. **Config bootstrap race.** The stack frames were
   `@wdio/cli … tsConfigPathFromConfigFile → ConfigParser.initialize` (the CLI's
   own bootstrap path builds a `ConfigParser` *before* the real run to read
   `tsConfigPath`). The process that started second died there, before any
   session existed. That bootstrap re-enters config loading on shared toolchain
   state (TS config resolution / ts-node cache) and is **not concurrency-safe** on
   this toolchain — whichever run loses reports the config load, not a test
   failure, which is why the symptom looked environmental.
2. **Sandbox lock contention.** Concurrently started WebView2 runtimes left
   orphaned `msedgewebview2.exe` processes holding each sandbox's `EBWebView`
   lock; the next app instance then exits at start
   (`session deleted as the browser has closed the connection`). `npm run
   e2e:clean` kills app/driver processes but not WebView2.

Which of the two hit depended on timing — that is why the same commit passed in
one checkout and failed in another. The current harness removes both causes by
construction: one instance at a time (sequential), and `killStale()` kills anything
whose command line names that instance's sandbox before and after each run. It is
not "fixed by retrying"; the contention no longer exists, and the suite is
deterministic enough to assert exact sequence numbers.
